# Гайд по MQTT

## 1. Что такое MQTT и зачем он нужен

**MQTT (Message Queuing Telemetry Transport)** — это легковесный протокол обмена сообщениями по принципу «публикация/подписка» (publish/subscribe), разработанный для устройств с ограниченными ресурсами и ненадёжных сетей. Протокол был создан инженерами IBM Энди Стэнфорд-Кларком и Арленом Ниппером в 1999 году для мониторинга нефтепроводов через спутниковую связь, где пропускная способность была ограничена, а надёжность соединения нельзя было гарантировать.

В 2013 году IBM передала протокол организации OASIS для стандартизации, и в ноябре 2014 года версия 3.1.1 была ратифицирована как международный стандарт. В 2019 году вышла версия 5.0 с улучшенной обработкой ошибок, управлением сессиями и расширенными свойствами сообщений.

**Ключевые особенности:**

- Минимальные накладные расходы: фиксированный заголовок может занимать всего 2 байта, что делает MQTT пригодным для микроконтроллеров с килобайтами оперативной памяти.
- Работа поверх TCP/IP (или другого протокола с упорядоченной, без потерь, двунаправленной передачей).
- Асимметричная модель связи: издатель и подписчик не знают друг о друге и работают независимо.
- Поддержка гарантий доставки (QoS) и «завещания» (Last Will and Testament).

**Где применяется MQTT:**

- Промышленный IoT: мониторинг оборудования, предиктивное обслуживание.
- Умный дом: датчики температуры, освещения, системы безопасности.
- Телеметрия: сбор данных с удалённых объектов (нефтепроводы, метеостанции, транспорт).
- Мобильные приложения: push-уведомления, чаты, обмен данными в реальном времени.
- Интеграция корпоративных систем: SAP, Azure IoT Hub и другие платформы поддерживают MQTT как транспортный протокол.

## 2. Как устроен MQTT и как он работает

### 2.1. Архитектура: брокер и клиенты

В любой MQTT-сети обязательно присутствует **брокер** (Message Broker) и произвольное количество **клиентов** (Clients).

- **Брокер** — центральный узел, который принимает сообщения от издателей и рассылает их подписчикам. Без брокера сеть не работает.
- **Клиент** — любое устройство или приложение, которое подключается к брокеру. Клиент может одновременно и публиковать сообщения, и подписываться на них.

Клиенты не обмениваются данными напрямую — вся коммуникация идёт через брокер. Это обеспечивает **развязку** (decoupling): издатель не знает, кто получит его сообщение, а подписчик не знает, кто его отправил.

### 2.2. Модель публикации/подписки и топики

Сообщения в MQTT публикуются в **топики** — иерархические строки, разделённые слэшами, например: `sensors/building1/floor3/temperature`.

Топики **не нужно создавать заранее** — достаточно опубликовать в них сообщение. Иерархия напоминает файловую систему, что позволяет логически организовывать данные.

**Подписка с подстановочными знаками:**

- `+` — одноуровневый подстановочный знак. Например, `sensors/+/temperature` подпишет на температуру всех датчиков любого объекта.
- `#` — многоуровневый подстановочный знак (только в конце). Например, `sensors/#` подпишет на все сообщения, начинающиеся с `sensors/`.

Пример: для топика `a/b/c/d` подписка `a/+/c/d` совпадёт, а `a/b/c` — нет.

### 2.3. Уровни качества обслуживания (QoS)

MQTT определяет три уровня гарантии доставки:

| Уровень | Название | Гарантия | Когда использовать |
|---------|----------|----------|-------------------|
| QoS 0 | At most once | Не более одного раза (без подтверждения) | Частые показания датчиков, где потеря отдельного значения допустима |
| QoS 1 | At least once | Не менее одного раза (с подтверждением) | Важные данные, где дубликаты не критичны |
| QoS 2 | Exactly once | Ровно один раз (четырёхэтапное рукопожатие) | Команды и транзакции, где дубликаты недопустимы |

QoS 2 использует четырёхэтапный обмен (PUBLISH → PUBREC → PUBREL → PUBCOMP), что увеличивает задержку, но гарантирует отсутствие дубликатов.

### 2.4. Управление сессиями и Last Will

**Persistent Session:** клиент может запросить постоянную сессию при подключении. Брокер сохранит подписки и недоставленные сообщения QoS 1/2 и доставит их при переподключении.

**Last Will and Testament (LWT):** клиент может заранее зарегистрировать «завещание» — сообщение, которое брокер опубликует автоматически, если клиент отключится неожиданно. Это используется для обнаружения сбоев в распределённых системах.

### 2.5. Безопасность

MQTT работает поверх TCP/IP и может быть защищён с помощью **TLS**, который шифрует соединение и аутентифицирует брокера перед клиентом.

Аутентификация клиентов возможна двумя способами:

- **Логин/пароль** — передаётся в самом протоколе MQTT.
- **Клиентские сертификаты** — на уровне TLS.

MQTT 5.0 добавила улучшенные схемы аутентификации, поддерживающие challenge-response механизмы, выходящие за рамки простого обмена паролями.

Протокол также может работать через **WebSockets** (MQTT over WS), что позволяет браузерным клиентам подключаться к брокерам через стандартные HTTPS-порты.

## 3. Как взаимодействовать с MQTT

### 3.1. Выбор брокера

Для начала работы нужен MQTT-брокер. Популярные варианты:

- **Mosquitto** — лёгкий брокер с открытым исходным кодом, работает на Raspberry Pi и малых системах.
- **EMQX** — масштабируемый брокер для промышленного IoT, доступен бесплатный публичный сервер `broker.emqx.io`.
- **HiveMQ** — коммерческий брокер с обширной документацией и бесплатным публичным брокером `broker.hivemq.com`.
- **Azure IoT Hub**, **AWS IoT Core**, **Google Cloud IoT** — облачные платформы со встроенной поддержкой MQTT.

Для обучения и тестирования можно использовать публичные брокеры: `broker.emqx.io` (порт 1883 для TCP, 8883 для SSL/TLS).

### 3.2. Клиентские библиотеки

MQTT-клиенты доступны практически для всех языков программирования. Наиболее распространённые:

| Язык | Библиотека | Пример |
|------|-----------|--------|
| Python | `paho-mqtt` | `pip install paho-mqtt` |
| JavaScript | `mqtt.js` | `npm install mqtt` |
| C/C++ | `Paho MQTT C` | Для встраиваемых систем |
| PHP | `php-mqtt/client` | `composer require php-mqtt/client` |
| C# | `MQTTnet` | Для .NET-приложений |
| Java | `Eclipse Paho Java` | Для Android и серверных приложений |

### 3.3. Базовый сценарий работы

Типичный цикл работы с MQTT включает следующие шаги:

1. **Подключение к брокеру** — клиент отправляет пакет CONNECT, брокер отвечает CONNACK.
2. **Подписка** — клиент отправляет SUBSCRIBE с указанием топика (или шаблона), брокер подтверждает SUBACK.
3. **Публикация** — издатель отправляет PUBLISH с топиком и полезной нагрузкой. Брокер пересылает сообщение всем подписчикам, чьи подписки совпадают с топиком.
4. **Получение сообщений** — подписчик получает PUBLISH через функцию обратного вызова (callback).
5. **Отключение** — клиент отправляет DISCONNECT (или соединение разрывается, и срабатывает LWT).

### 3.4. Пример на Python (paho-mqtt)

```python
import paho.mqtt.client as mqtt

# Подключение к публичному брокеру
broker = "broker.emqx.io"
port = 1883

def on_connect(client, userdata, flags, rc):
    print(f"Подключено с кодом: {rc}")
    client.subscribe("test/topic")

def on_message(client, userdata, msg):
    print(f"Получено: {msg.topic} -> {msg.payload.decode()}")

client = mqtt.Client()
client.on_connect = on_connect
client.on_message = on_message

client.connect(broker, port, 60)
client.publish("test/topic", "Привет, MQTT!")

client.loop_forever()
```

Этот код подключается к публичному брокеру EMQX, подписывается на топик `test/topic`, публикует сообщение и выводит все полученные сообщения.

### 3.5. Инструменты для отладки

- **MQTTX** — кроссплатформенный клиент от EMQX с графическим интерфейсом.
- **MQTT Explorer** — визуальный инструмент для просмотра дерева топиков и сообщений.
- **mosquitto_pub / mosquitto_sub** — консольные утилиты из состава брокера Mosquitto.
- **HiveMQ WebSocket Client** — веб-клиент для быстрого тестирования.

## 5. Сравнение MQTT с другими протоколами

| Критерий | MQTT | HTTP | AMQP | CoAP |
|----------|------|------|------|------|
| Модель | Pub/Sub | Request/Response | Pub/Sub, очередь | Request/Response |
| Транспорт | TCP | TCP | TCP | UDP |
| Накладные расходы | Очень низкие | Высокие | Средние | Очень низкие |
| QoS | 0, 1, 2 | Нет | Есть | Есть |
| Идеален для | IoT, телеметрия | Веб, API | Корпоративные очереди | Сенсорные сети |

MQTT выигрывает за счёт минимального заголовка и гибкой модели pub/sub, что делает его оптимальным выбором для устройств с ограниченными ресурсами.

## 6. Рекомендации по проектированию топиков

- **Используйте иерархию:** `{страна}/{город}/{объект}/{датчик}/{показатель}` — например, `ru/moscow/factory1/boiler/temperature`.
- **Избегайте ведущих слэшей:** `/sensors/temp` и `sensors/temp` — разные топики.
- **Не используйте пробелы и специальные символы** (кроме `/`, `+`, `#`).
- **Применяйте подстановочные знаки с осторожностью:** `#` в конце подписки может привести к получению большого объёма данных.
- **Для команд используйте отдельную ветку:** например, `commands/{device_id}/set`.

## 8. Заключение

MQTT — это зрелый, стандартизированный и широко поддерживаемый протокол, который стал де-факто стандартом для IoT-коммуникаций. Его лёгкость, гибкая модель pub/sub и встроенные механизмы надёжности делают его идеальным выбором для проектов любого масштаба — от одного датчика на Arduino до промышленной платформы с миллионами устройств.

Для быстрого старта достаточно выбрать публичный брокер (например, `broker.emqx.io`), установить клиентскую библиотеку под нужный язык и следовать базовому сценарию: подключиться, подписаться, публиковать и обрабатывать сообщения. Все необходимые ссылки на документацию собраны в разделе 7.

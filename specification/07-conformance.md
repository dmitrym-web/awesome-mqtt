# 7. Цели соответствия (Conformance)

## 7.1. Соответствие

MQTT-спецификация определяет требования к двум типам участников:

- **MQTT-клиент** — приложение или устройство, использующее протокол для подключения к серверу.
- **MQTT-сервер** (брокер) — программа, принимающая подключения и обрабатывающая сообщения.

Соответствие **НЕ** оценивается целиком «клиент/сервер». Оно оценивается **по функциям**. Клиент **МОЖЕТ** поддерживать только часть протокола (например, только публиковать или только подписываться), но то, что он реализует, **ДОЛЖНО** соответствовать спецификации.

### 7.1.1. Соответствие клиента

Клиент считается соответствующим спецификации, если он:

1. Реализует **все обязательные** части протокола, которые относятся к его роли.
2. Правильно обрабатывает входящие пакеты.
3. Корректно формирует исходящие пакеты.
4. Соблюдает нормативные требования (обозначенные **ДОЛЖЕН**, **НЕ ДОЛЖЕН**).
5. Не полагается на необязательные функции, если они не согласованы с сервером.

Клиент, поддерживающий только подмножество (например, только publisher), **МОЖЕТ** считаться соответствующим, если поддерживаемое подмножество реализовано корректно.

### 7.1.2. Соответствие сервера

Сервер считается соответствующим спецификации, если он:

1. Реализует **все обязательные** части протокола.
2. Правильно обрабатывает CONNECT, PUBLISH, SUBSCRIBE и остальные пакеты.
3. Соблюдает требования к сессии, QoS-потокам, retain, Will.
4. Возвращает корректные Reason Codes.
5. Обрабатывает ошибки согласно спецификации.
6. Поддерживает все обязательные свойства протокола.

Сервер **НЕ** имеет права на «частичное» соответствие по обязательным функциям — он либо поддерживает функцию полностью, либо объявляет её как недоступную (через свойства CONNACK: Maximum QoS, Retain Available, Wildcard Subscription Available и т.д.).

## 7.2. Обязательные утверждения

Спецификация содержит множество нормативных утверждений вида **«X ДОЛЖЕН делать Y»**. Они делятся на несколько категорий.

### 7.2.1. Ключевые слова нормативности

- **ДОЛЖЕН (MUST)** — обязательно.
- **НЕ ДОЛЖЕН (MUST NOT)** — запрещено.
- **СЛЕДУЕТ (SHOULD)** — рекомендуется, но допускаются отступления с обоснованием.
- **НЕ СЛЕДУЕТ (SHOULD NOT)** — не рекомендуется.
- **МОЖЕТ (MAY)** — опционально.

Все обязательные требования вынесены в **Приложение B. Обязательные нормативные утверждения**.

### 7.2.2. Примеры обязательных требований

Для клиента:

- Клиент **ДОЛЖЕН** отправлять CONNECT первым пакетом.
- Клиент **ДОЛЖЕН** отправлять PINGREQ при отсутствии активности дольше Keep Alive.
- Клиент **ДОЛЖЕН** обрабатывать PUBACK, PUBREC, PUBREL, PUBCOMP при работе с QoS 1 и 2.
- Клиент **НЕ ДОЛЖЕН** отправлять два CONNECT в одном соединении.
- Клиент **ДОЛЖЕН** отправлять SUBSCRIBE только с корректными фильтрами.

Для сервера:

- Сервер **ДОЛЖЕН** отвечать CONNACK на CONNECT.
- Сервер **ДОЛЖЕН** закрывать соединение при получении некорректного пакета.
- Сервер **ДОЛЖЕН** сохранять retained-сообщения (при поддержке retain).
- Сервер **ДОЛЖЕН** доставлять сообщения подписчикам согласно их подпискам.
- Сервер **ДОЛЖЕН** корректно обрабатывать Session Expiry Interval.

### 7.2.3. Соответствие по функциям

Спецификация определяет несколько областей, где соответствие оценивается отдельно:

- **QoS 0** — обязательна для всех клиентов и серверов.
- **QoS 1** — обязательна для всех, кто публикует или принимает с этим уровнем.
- **QoS 2** — обязательна, если поддерживается.
- **Retain** — необязательно; сервер объявляет поддержку через Retain Available.
- **Wildcard Subscriptions** — необязательно; объявляется через Wildcard Subscription Available.
- **Subscription Identifiers** — необязательно.
- **Shared Subscriptions** — необязательно.
- **Topic Alias** — необязательно.
- **Расширенная аутентификация** — необязательно.
- **WebSocket transport** — необязательно, но если поддерживается — по правилам раздела 6.

Если сервер не поддерживает какую-то опциональную функцию, он **ДОЛЖЕН** явно сообщить об этом клиенту через CONNACK:

- **Retain Available = 0** — retain не поддерживается.
- **Wildcard Subscription Available = 0** — подстановочные знаки в подписках не поддерживаются.
- **Subscription Identifiers Available = 0** — Subscription Identifier не поддерживаются.
- **Shared Subscription Available = 0** — общие подписки не поддерживаются.
- **Maximum QoS = 0 или 1** — максимально поддерживаемый QoS.
- **Topic Alias Maximum = 0** — псевдонимы топиков не поддерживаются.

### 7.2.4. Поведение при неподдерживаемых функциях

Если клиент использует функцию, которая не поддерживается сервером:

| Функция | Ответ сервера |
|---------|---------------|
| QoS выше Maximum QoS | Отказ: PUBACK/PUBREC с 0x9B (QoS not supported) или закрытие соединения |
| Retain при Retain Available = 0 | Отказ: PUBACK/PUBREC с 0x9A (Retain not supported) |
| Wildcards при Wildcard Subscription Available = 0 | SUBACK с 0xA2 |
| Subscription Identifier при Available = 0 | SUBACK с 0xA1 |
| Shared Subscriptions при Available = 0 | SUBACK с 0x9E |
| Topic Alias больше Topic Alias Maximum | DISCONNECT с 0x94 |
| Неподдерживаемый Authentication Method | CONNACK с 0x8C |

## 7.3. Что не входит в соответствие

Следующие аспекты **НЕ** регулируются спецификацией и остаются на усмотрение реализации:

- **Хранение данных:** как брокер хранит retained-сообщения и сессии (в памяти, на диске).
- **Производительность:** максимальное число подключений, пропускная способность.
- **Кластеризация:** как брокеры объединяются в кластер.
- **Мониторинг:** метрики, логи, трассировка.
- **Схемы авторизации:** правила ACL не описываются спецификацией.
- **Форматы payload:** содержимое сообщений — ответственность приложения.
- **Оптимизации транспорта:** TCP_NODELAY, буферизация и т.п.
- **Управление ресурсами:** лимиты памяти, таймауты, квоты.

Эти вопросы решаются производителями брокеров и клиентских библиотек.

## 7.4. Как проверить соответствие

### 7.4.1. Автоматизированное тестирование

Существуют наборы тестов для проверки соответствия MQTT:

- **Eclipse Paho Compliance Tests** — тесты для клиентов.
- **MQTT Conformance Test Suite** — тесты для брокеров.
- **Собственные тесты** — наборы сценариев для конкретных функций.

### 7.4.2. Проверка вручную

Ключевые проверки:

1. **CONNECT/CONNACK:** корректные Reason Codes, Session Present, свойства.
2. **QoS 0, 1, 2:** полные протокольные потоки, повторные передачи, обработка таймаутов.
3. **Retain:** сохранение, доставка новым подписчикам, удаление через пустой payload.
4. **Will:** публикация при аномальном отключении, отсутствие при нормальном.
5. **Сессии:** сохранение подписок и недоставленных сообщений при переподключении.
6. **Ошибки:** корректное закрытие соединения, DISCONNECT с нужным кодом.
7. **Subscriptions:** Wildcards, Shared Subscriptions, Subscription Identifiers, NL, RAP.
8. **Свойства:** все свойства пакетов, порядок, обязательность.
9. **Keep Alive:** корректный таймаут, поведение при неактивности.
10. **WebSocket:** согласование подпротокола, работа через фрагментацию фреймов.

### 7.4.3. Инструменты

- **MQTTX** — ручное тестирование пакетов.
- **mosquitto_pub / mosquitto_sub** — простые сценарии.
- **Wireshark** — анализ трафика.
- **Логи брокера** — проверка поведения на стороне сервера.

## 7.5. Итог

Соответствие MQTT-спецификации — это не бинарный статус «соответствует/не соответствует» для всего продукта, а набор отдельных заявлений:

- Реализует ли клиент/сервер **обязательные** части?
- Поддерживает ли он **опциональные** функции?
- Правильно ли он объявляет поддержку через CONNACK?

Спецификация даёт производителям свободу в реализации, но жёстко фиксирует **наблюдаемое поведение** участников — то, что видно на проводе. Именно это поведение и проверяется на соответствие.

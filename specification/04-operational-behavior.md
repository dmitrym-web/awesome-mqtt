# 4. Операционное поведение

Раздел описывает, как клиенты и серверы взаимодействуют в процессе работы. Из-за объёма разбит на несколько выпусков:

- **Выпуск 1:** 4.1 Состояние сессии, 4.2 Сетевые соединения, 4.3 Уровни QoS и протокольные потоки
- **Выпуск 2:** 4.4 Повторная передача сообщений, 4.5 Приём сообщений, 4.6 Порядок сообщений
- **Выпуск 3:** 4.7 Имена топиков и фильтры, 4.8 Параметры подписки, 4.9 Управление потоком
- **Выпуск 4 (в этом файле, завершающий):** 4.10 Request/Response, 4.11 Перенаправление сервера, 4.12 Расширенная аутентификация, 4.13 Обработка ошибок

---

## 4.1. Состояние сессии

### 4.1.1. Состояние сессии на клиенте

Клиент **ДОЛЖЕН** хранить:

- Все сообщения QoS 1 и QoS 2, отправленные, но ещё не получившие полного подтверждения.
- Все сообщения QoS 2, полученные, но ещё не завершённые.
- Все подписки, связанные с данной сессией.

Клиент **МОЖЕТ** хранить сообщения QoS 0. После завершения сессии всё удаляется.

### 4.1.2. Состояние сессии на сервере

Сервер **ДОЛЖЕН** хранить:

- Факт существования сессии.
- Все подписки клиента.
- Все сообщения QoS 1 и QoS 2, ожидающие подтверждения.
- Все сообщения QoS 2, полученные, но не завершённые.
- Ожидающие доставки сообщения QoS 1/2 для persistent session.

Сервер **НЕ ДОЛЖЕН** хранить сообщения по истечении Message Expiry Interval.

### 4.1.3. Session Expiry Interval

| Значение | Поведение |
|----------|-----------|
| 0 | Сессия завершается при отключении |
| 1 – 0xFFFFFFFE | Сессия хранится указанное число секунд |
| 0xFFFFFFFF | Сессия хранится бессрочно |

Сервер **МОЖЕТ** уменьшить значение, но **НЕ ДОЛЖЕН** увеличивать.

### 4.1.4. Завершение сессии

При истечении Session Expiry; DISCONNECT с Session Expiry = 0; новом CONNECT с тем же Client Identifier и Clean Start = 1; подключении с тем же Client Identifier.

---

## 4.2. Сетевые соединения

### 4.2.1. Установка соединения

TCP → CONNECT → CONNACK. Если Reason Code ≠ 0x00 — закрытие.

### 4.2.2. Обработка нескольких подключений

При том же Client Identifier сервер закрывает старое соединение (DISCONNECT 0x8E) и устанавливает новое.

### 4.2.3. Keep Alive

Клиент **ДОЛЖЕН** отправлять пакет в течение Keep Alive. Сервер разрывает после 1.5 × Keep Alive.

### 4.2.4. Разрыв соединения

Нормальный (DISCONNECT) — Will не публикуется. Аномальный — публикуется.

---

## 4.3. Уровни QoS и протокольные потоки

### 4.3.1. QoS 0

```
Издатель ── PUBLISH ──▶ Сервер ── PUBLISH ──▶ Подписчик
```

### 4.3.2. QoS 1

```
PUBLISH(id) → PUBACK(id)
```

### 4.3.3. QoS 2

```
PUBLISH → PUBREC → PUBREL → PUBCOMP
```

### 4.3.4. Понижение QoS

Сервер **МОЖЕТ** понизить до значения в подписке. Повышать — **НЕ ДОЛЖЕН**.

### 4.3.5. Retained сообщения

При RETAIN = 1 сервер сохраняет сообщение. При новой подписке — доставляет с RETAIN = 1. Пустая нагрузка с RETAIN = 1 удаляет retained.

---

## 4.4. Повторная передача сообщений

### 4.4.1. Повторная передача при QoS 1

Повтор PUBLISH с DUP = 1 до PUBACK. Получатель не доставляет повторно, но подтверждает.

### 4.4.2. Повторная передача при QoS 2

Повтор PUBLISH до PUBREC; повтор PUBREL до PUBCOMP.

### 4.4.3. Правила обработки повторных PUBLISH

Флаг DUP — только в PUBLISH. Для QoS 0 = 0. Packet Identifier уникален в сессии.

### 4.4.4. Повторная передача и сессия

При возобновлении сессии отправитель повторяет неподтверждённые PUBLISH и PUBREL.

---

## 4.5. Приём сообщений

### 4.5.1. Обработка входящих PUBLISH

QoS 0 — доставить. QoS 1 — доставить и PUBACK. QoS 2 — сохранить id, PUBREC, при PUBREL — PUBCOMP.

### 4.5.2. Порядок обработки QoS 2

Два подхода: доставка при PUBLISH или при PUBREL. Оба совместимы.

### 4.5.3. Обработка некорректных пакетов

Получатель **ДОЛЖЕН** закрыть соединение при нарушении формата или встрече неизвестного свойства.

### 4.5.4. Обработка отсутствия подписчиков

Сообщение отбрасывается. В PUBACK/PUBREC **МОЖЕТ** быть код 0x10.

### 4.5.5. Обработка переполнения Receive Maximum

DISCONNECT с кодом 0x93 и закрытие.

---

## 4.6. Порядок сообщений

### 4.6.1. Порядок от одного отправителя

Гарантирован при: одном топике, одинаковом QoS (1 или 2), одном соединении.

### 4.6.2. Повторная передача и порядок

Повтор не обгоняет более новые сообщения.

### 4.6.3. Порядок и несколько подписок

Только в рамках одного фильтра.

### 4.6.4. Порядок и retained-сообщения

Retained — после SUBACK. Порядок относительно обычных не гарантирован.

---

## 4.7. Имена топиков и фильтры

### 4.7.1. Имена топиков

- Минимум 1 символ, максимум 65535 байт.
- **НЕ ДОЛЖНО** содержать `+`, `#`, U+0000.
- **МОЖЕТ** содержать `/`.
- Различается регистр. `/a`, `a/`, `a` — три разных топика.

### 4.7.2. Фильтры топиков

- Минимум 1 символ, максимум 65535 байт.
- **НЕ ДОЛЖЕН** содержать U+0000.
- **МОЖЕТ** содержать `+`, `#`.

### 4.7.3. Одноуровневый `+`

Соответствует одному уровню.

| Фильтр | Совпадёт |
|--------|----------|
| `sport/tennis/+` | `sport/tennis/player1` |
| `sport/+` | `sport/` |
| `+/+` | `a/b` |

### 4.7.4. Многоуровневый `#`

Соответствует нулю или более уровней. Только последний символ.

| Фильтр | Совпадёт |
|--------|----------|
| `sport/tennis/#` | `sport/tennis`, `sport/tennis/player1` |
| `sport/#` | `sport`, `sport/tennis` |
| `#` | все топики (кроме начинающихся с `$`) |

Некорректные: `sport/tennis#`, `sport/#/ranking`.

### 4.7.5. Разделитель `/`

Создаёт уровни. `a//b` = три уровня. `a/` = `a` + пустой.

### 4.7.6. Топики с `$`

Фильтры `#` и `+` в начале **НЕ** совпадают с топиками `$SYS/...`. Нужно явно `$SYS/#`.

### 4.7.7. Сопоставление

Разбить по `/`, пройти параллельно, `+` = один уровень, `#` = остаток. Разная длина без `#` = не совпадение.

---

## 4.8. Параметры подписки

### 4.8.1. Maximum QoS

Сервер доставляет с QoS не выше, чем в подписке.

### 4.8.2. No Local (NL)

NL = 1 — не доставлять клиенту его же публикации. Несовместим с общими подписками.

### 4.8.3. Retain As Published (RAP)

RAP = 0 — обнулять RETAIN при доставке. RAP = 1 — сохранять.

### 4.8.4. Retain Handling

| Значение | Поведение |
|---------:|-----------|
| 0 | Отправлять retained при подписке |
| 1 | Отправлять только для новой подписки |
| 2 | Не отправлять |
| 3 | Зарезервировано |

### 4.8.5. Subscription Identifier

1 – 268 435 455. Включается в PUBLISH при доставке. Может быть несколько, если сообщение попадает под несколько подписок.

### 4.8.6. Общие подписки (Shared Subscriptions)

Формат: `$share/{ShareName}/{TopicFilter}`.

- Сообщение доставляется только одному клиенту группы.
- NL не используется.
- Retained — каждому клиенту группы.
- Если не поддерживается — SUBACK 0x9E.

---

## 4.9. Управление потоком

### 4.9.1. Receive Maximum

Ограничивает число неподтверждённых QoS 1/2. По умолчанию 65535. 0 запрещено.

### 4.9.2. Превышение Receive Maximum

DISCONNECT 0x93 и закрытие.

### 4.9.3. Maximum Packet Size

Максимальный размер принимаемого пакета. 0 запрещено.

### 4.9.4. Topic Alias Maximum и Topic Alias

Псевдоним топика (1 – Topic Alias Maximum). Действует в рамках одного соединения. Первый PUBLISH с псевдонимом содержит и Topic Name, и Topic Alias; последующие — только псевдоним. Превышение — DISCONNECT 0x94.

---

## 4.10. Request/Response

MQTT 5.0 формально определяет шаблон «запрос/ответ» поверх pub/sub. Используется для сценариев, где клиент отправляет запрос и ожидает ответ в отдельный топик.

### 4.10.1. Response Topic

Свойство **Response Topic** в PUBLISH задаёт топик, в который должен быть отправлен ответ. Это UTF-8 строка, удовлетворяющая требованиям к имени топика (без подстановочных знаков).

Правило: клиент, получивший запрос с Response Topic, **ДОЛЖЕН** отправить ответ именно в этот топик.

### 4.10.2. Correlation Data

Свойство **Correlation Data** — двоичные данные, помогающие сопоставить ответ с конкретным запросом.

Правила:

- **ДОЛЖНО** присутствовать только вместе с Response Topic.
- Клиент, отвечающий на запрос, **ДОЛЖЕН** скопировать Correlation Data в ответ без изменений.
- Запрос без Correlation Data допускается, но тогда сопоставление — на усмотрение приложения.

### 4.10.3. Порядок Request/Response

Клиент A публикует запрос:

```
PUBLISH
  Topic: "requests/device1"
  Response Topic: "responses/clientA"
  Correlation Data: 0xAB12CD
  Payload: <тело запроса>
```

Клиент B, подписанный на `requests/device1`, публикует ответ:

```
PUBLISH
  Topic: "responses/clientA"
  Correlation Data: 0xAB12CD
  Payload: <тело ответа>
```

Клиент A, подписанный на `responses/clientA`, получает ответ и по Correlation Data находит исходный запрос.

### 4.10.4. Response Information

Свойство **Response Information** в CONNACK задаёт базовый префикс топика для ответов. Клиент **МОЖЕТ** использовать его для построения Response Topic.

Например, сервер возвращает `Response Information = "reply/"`. Тогда клиент может использовать `reply/clientA` как Response Topic.

### 4.10.5. Ограничения

- Response Topic **НЕ ДОЛЖЕН** содержать подстановочных знаков.
- Correlation Data **НЕ ДОЛЖНО** использоваться без Response Topic.
- Retained-флаг для запросов обычно не применяется (ответы — тоже).

## 4.11. Перенаправление сервера

MQTT 5.0 позволяет серверу указать клиенту на другой сервер или сообщить о перемещении.

### 4.11.1. Server Reference

Свойство **Server Reference** (UTF-8) содержит адрес другого сервера. Может появляться в CONNACK или DISCONNECT.

- Если в CONNACK вместе с Reason Code 0x9C (Use another server) или 0x9D (Server moved) — клиент **ДОЛЖЕН** подключиться к указанному серверу.
- Если в DISCONNECT — клиент **ДОЛЖЕН** переподключиться к указанному адресу.

Формат адреса — на усмотрение реализации (обычно `host:port`).

### 4.11.2. Use another server (0x9C)

Сервер сообщает, что текущий узел не может обслуживать клиента, но есть другой. Клиент **ДОЛЖЕН** попытаться подключиться к серверу из Server Reference.

Если Server Reference отсутствует — клиент **МОЖЕТ** попытаться снова или выбрать другой узел самостоятельно.

### 4.11.3. Server moved (0x9D)

Постоянное перемещение. Клиент **ДОЛЖЕН** обновить свой адрес и больше не возвращаться к старому узлу.

### 4.11.4. Обработка на клиенте

1. Получив CONNACK с 0x9C или 0x9D — закрыть текущее соединение.
2. Извлечь Server Reference.
3. Установить новое соединение с указанным адресом.
4. Повторить CONNECT.

Защита от зацикливания — на усмотрение клиента (например, ограничение числа попыток).

## 4.12. Расширенная аутентификация

MQTT 5.0 позволяет использовать произвольные схемы аутентификации (SASL-подобные) через пакет AUTH.

### 4.12.1. Authentication Method

Свойство **Authentication Method** (UTF-8) задаёт имя метода. Передаётся в CONNECT (клиент) и CONNACK (сервер). Все последующие AUTH **ДОЛЖНЫ** использовать тот же метод.

Если сервер не поддерживает метод из CONNECT — CONNACK с Reason Code 0x8C (Bad authentication method).

### 4.12.2. Authentication Data

Свойство **Authentication Data** (Binary Data) содержит полезные данные метода. **НЕ ДОЛЖНО** появляться без Authentication Method.

Формат данных определяется методом.

### 4.12.3. Поток аутентификации при подключении

1. Клиент отправляет CONNECT с Authentication Method и, возможно, Authentication Data.
2. Сервер **МОЖЕТ** ответить AUTH с Reason Code 0x18 (Continue authentication).
3. Клиент **ДОЛЖЕН** ответить AUTH.
4. Обмен продолжается, пока одна из сторон не завершит его.
5. Сервер отправляет CONNACK (0x00 = успех, ≥ 0x80 = ошибка).

Если обмен завершён успешно — соединение установлено. Иначе — закрыто.

### 4.12.4. Переаутентификация

После установки соединения клиент или сервер **МОЖЕТ** инициировать переаутентификацию, отправив AUTH с Reason Code 0x19 (Re-authenticate).

Правила:

- Обмен идёт так же, как при подключении.
- **НЕ ДОЛЖЕН** прерывать обработку уже начатых операций.
- При успехе обе стороны продолжают работу.
- При ошибке — DISCONNECT и закрытие.
- Во время переаутентификации разрешено обмениваться другими пакетами.

### 4.12.5. Ограничения

- AUTH **МОЖЕТ** использоваться только если был указан Authentication Method.
- Если Authentication Method не был задан — AUTH запрещён, соединение разрывается.
- Пакет AUTH не имеет полезной нагрузки.

## 4.13. Обработка ошибок

### 4.13.1. Reason Codes в подтверждениях

MQTT 5.0 включает Reason Code в большинство подтверждающих пакетов:

- PUBACK, PUBREC, PUBREL, PUBCOMP — для QoS-потоков.
- SUBACK, UNSUBACK — для операций с подписками.
- CONNACK, DISCONNECT — для соединения.
- AUTH — для аутентификации.

Значения:

- 0x00 – 0x7F — успех (разные варианты).
- 0x80 – 0xFF — ошибка.

### 4.13.2. Reason String

Свойство **Reason String** (UTF-8) содержит текст с описанием причины. Используется для отладки. **НЕ ДОЛЖНО** анализироваться программно — только для логов.

Если Request Problem Information = 0, сервер **НЕ ДОЛЖЕН** отправлять Reason String в пакетах, кроме PUBLISH, CONNACK, DISCONNECT.

### 4.13.3. Обработка ошибок в QoS

При ошибке на этапе QoS 2:

- Если PUBREC получен с кодом ≥ 0x80 — отправитель **ДОЛЖЕН** прекратить процедуру (не отправлять PUBREL) и считать публикацию завершённой с ошибкой.
- Если PUBREL получен с кодом ≥ 0x80 — получатель **ДОЛЖЕН** удалить сохранённое состояние и не отправлять PUBCOMP.

### 4.13.4. Обработка ошибок в SUBSCRIBE

- Если ошибка касается конкретного фильтра — Reason Code ≥ 0x80 для этого фильтра, остальные обрабатываются нормально.
- Если ошибка касается всего пакета (например, некорректный формат) — сервер **ДОЛЖЕН** закрыть соединение.

### 4.13.5. Обработка ошибок в DISCONNECT

- DISCONNECT с кодом ≥ 0x80 указывает на причину, по которой соединение закрывается.
- После отправки DISCONNECT обе стороны **ДОЛЖНЫ** закрыть соединение.
- Will-сообщение публикуется при кодах, отличных от 0x00 (Normal disconnection). При 0x04 (Disconnect with Will Message) — публикуется обязательно.

### 4.13.6. Фатальные ошибки

Ряд ошибок требует закрытия соединения без попыток восстановления:

- Некорректный формат пакета (Malformed Packet 0x81).
- Нарушение протокола (Protocol Error 0x82).
- Превышение Maximum Packet Size.
- Неизвестное свойство.
- Некорректный Remaining Length.
- Отсутствие обязательного поля.

При таких ошибках сторона **ДОЛЖНА**:

1. Отправить DISCONNECT с соответствующим Reason Code.
2. Закрыть соединение.

### 4.13.7. Обработка на клиенте

Клиент **ДОЛЖЕН**:

1. Проверять Reason Codes в CONNACK, SUBACK, PUBACK и других пакетах.
2. Реагировать на ошибки согласно сценарию (повтор, отказ, переподключение).
3. Логировать Reason String для диагностики.

### 4.13.8. Обработка на сервере

Сервер **ДОЛЖЕН**:

1. Проверять корректность каждого входящего пакета.
2. Возвращать соответствующие Reason Codes.
3. Разрывать соединение при фатальных ошибках.
4. Не падать при некорректных входных данных (изоляция ошибок).

# 5. Безопасность

## 5.1. Обзор

MQTT — это протокол обмена сообщениями, работающий поверх транспортного соединения. Он **НЕ** предоставляет собственных механизмов шифрования, целостности или авторизации на уровне протокола (за исключением базовой передачи логина/пароля и расширенной аутентификации через AUTH). Вся защита строится на:

1. **Транспортном уровне** (обычно TLS).
2. **Аутентификации** — проверке, что клиент (или сервер) тот, за кого себя выдаёт.
3. **Авторизации** — проверке, что аутентифицированный клиент имеет право на действия, которые выполняет.
4. **Прикладном уровне** — контроле над содержимым полезной нагрузки.

MQTT-спецификация не навязывает конкретных схем безопасности. Её задача — предоставить точки расширения, куда эти схемы встраиваются.

## 5.2. Аутентификация

Аутентификация в MQTT может происходить на двух уровнях.

### 5.2.1. Аутентификация на транспортном уровне

Наиболее распространённый подход — использовать **TLS** с взаимной аутентификацией (mutual TLS, mTLS):

- Сервер предъявляет клиенту свой **сертификат сервера** — клиент убеждается, что подключается к легитимному брокеру.
- Клиент предъявляет серверу свой **клиентский сертификат** — сервер убеждается, что клиент легитимен.
- Обе стороны проверяют сертификаты через цепочку доверия (CA).

Преимущества:

- Пароли/токены не передаются в открытом виде.
- Защита от подмены сервера (MITM).
- Интеграция с существующей PKI.

Недостатки:

- Требует управления сертификатами.
- Не всегда применимо на устройствах с ограниченными ресурсами.

### 5.2.2. Аутентификация на уровне MQTT

MQTT предоставляет два механизма:

**Логин/пароль:**

- Передаётся в CONNECT (поля User Name и Password).
- Password — двоичные данные (может быть хешем, токеном и т.п.).
- **ДОЛЖНА** использоваться только поверх защищённого транспорта (TLS), иначе пароль виден в открытом виде.
- Простая, но негибкая.

**Расширенная аутентификация (MQTT 5.0):**

- Свойство **Authentication Method** задаёт схему.
- Обмен данными идёт через поле **Authentication Data** в CONNECT/CONNACK/AUTH.
- Позволяет реализовать SCRAM, SASL, challenge-response, OAuth-подобные схемы и др.
- Гибкая, но требует поддержки на обеих сторонах.

### 5.2.3. Рекомендации

- Использовать TLS **обязательно** при работе через публичные сети.
- Для устройств — клиентские сертификаты (mTLS).
- Для пользовательских приложений — логин/пароль поверх TLS.
- Для сложных схем — расширенная аутентификация MQTT 5.0.
- Никогда не использовать логин/пароль без TLS.

## 5.3. Авторизация

После аутентификации сервер **ДОЛЖЕН** проверить, имеет ли клиент право на запрошенные действия. Авторизация в MQTT — ответственность сервера, спецификация не описывает конкретных схем.

### 5.3.1. Объекты авторизации

Авторизация обычно применяется к:

- **Подключению:** может ли клиент вообще подключиться (по IP, по Client Identifier, по времени и т.п.).
- **Публикации:** имеет ли клиент право писать в конкретный топик.
- **Подписке:** имеет ли клиент право читать конкретный топик.
- **Состоянию сессии:** имеет ли клиент право использовать данный Client Identifier (защита от перехвата).

### 5.3.2. Уровни гранулярности

- **Глобальный:** всё или ничего.
- **По топику:** фильтры вида `sensors/device1/#` → read, `commands/device1/set` → write.
- **По операции:** только publish, только subscribe, оба.
- **По QoS:** максимально разрешённый уровень.
- **По retained:** разрешено ли публиковать retained.

### 5.3.3. Реализации

- **Списки контроля доступа (ACL)** — статические правила.
- **Динамические политики** — на основе базы данных пользователей/устройств.
- **Интеграция с внешними системами** (OAuth, LDAP, JWT-валидация).
- **Правила на уровне брокера** (например, в Mosquitto, EMQX, HiveMQ).

### 5.3.4. Обработка отказа

При отказе в авторизации сервер **ДОЛЖЕН**:

- При CONNECT — CONNACK с кодом 0x87 (Not authorized) и закрытие соединения.
- При PUBLISH — не публиковать, вернуть PUBACK/PUBREC с кодом 0x87.
- При SUBSCRIBE — вернуть SUBACK с кодом 0x87 для соответствующего фильтра.
- При UNSUBSCRIBE — вернуть UNSUBACK с кодом 0x87.

## 5.4. Целостность и конфиденциальность

### 5.4.1. Шифрование

MQTT сам по себе **НЕ** шифрует данные. Для защиты от прослушивания используется **TLS**:

- **TLS 1.2** — минимум.
- **TLS 1.3** — рекомендуется.
- Порт по умолчанию: **8883** (MQTT over TLS).
- Стандартный порт 1883 — **без** шифрования, использовать только в доверенных сетях.

### 5.4.2. Целостность

TLS обеспечивает:

- Проверку целостности сообщений (MAC/AEAD).
- Защиту от подмены пакетов в пути.
- Защиту от воспроизведения (в разумных пределах).

Без TLS пакеты MQTT **МОЖЕТ** подделать любой, кто имеет доступ к каналу.

### 5.4.3. Защита содержимого

Даже с TLS полезная нагрузка видна брокеру и всем, кому брокер её доставляет. Для сквозного шифрования (end-to-end) применяется прикладное шифрование:

- Полезная нагрузка шифруется на стороне издателя и расшифровывается на стороне подписчика.
- Брокер видит только шифротекст.
- Пример: шифрование JSON-payload симметричным ключом.
- Ключи **НЕ ДОЛЖНЫ** передаваться через MQTT в открытом виде.

### 5.4.4. Сертификаты

- Сертификаты **ДОЛЖНЫ** быть выпущены доверенным CA.
- Самоподписанные сертификаты **МОГУТ** использоваться в закрытых системах, но требуют ручного распространения корневого CA.
- Сроки действия **ДОЛЖНЫ** контролироваться; просроченные сертификаты приводят к отказам.
- Отзыв (CRL/OCSP) — на усмотрение инфраструктуры.

### 5.4.5. Пароли и токены

- Пароли **НЕ ДОЛЖНЫ** храниться в открытом виде.
- Хеширование на сервере: bcrypt, scrypt, argon2.
- Токены (JWT и подобные) **ДОЛЖНЫ** иметь ограниченный срок жизни.
- Пароли **НЕ ДОЛЖНЫ** логироваться.
- В цепочке «клиент→брокер→клиент» пароль **НЕ** передаётся дальше брокера.

### 5.4.6. Дополнительные меры

- **Rate limiting:** защита от флуда публикациями/подписками.
- **Ограничение размера пакета:** защита от DoS через большие пакеты.
- **Мониторинг:** логирование подключений, отказов авторизации, аномальной активности.
- **Изоляция:** отдельные инстансы брокера для разных клиентов/групп.
- **Обновления:** регулярное обновление брокера и клиентов.

## 5.5. Модель угроз

### 5.5.1. Основные угрозы

- **Прослушивание трафика** — MitM читает пакеты. Защита: TLS.
- **Подмена сервера** — клиент подключается к фальшивому брокеру. Защита: TLS с проверкой сертификата.
- **Подмена клиента** — злоумышленник выдаёт себя за легитимного клиента. Защита: mTLS или логин/пароль поверх TLS.
- **Перехват сессии** — использование чужого Client Identifier. Защита: авторизация Client Identifier, привязка к учётной записи.
- **Несанкционированная публикация/подписка** — клиент пишет/читает не туда. Защита: ACL.
- **DoS** — флуд пакетами, большими пакетами, множественными подключениями. Защита: rate limiting, размерные лимиты, квоты.
- **Утечка через retained** — retained-сообщение остаётся доступно после удаления клиента. Защита: контроль над retained-публикациями, очистка по политике.
- **Will-атака** — злоумышленник публикует ложное Will через разрыв чужой сессии. Защита: mTLS.

### 5.5.2. Особые соображения MQTT 5.0

- **Reason String** может раскрывать внутренние детали. При чувствительных сценариях — отключить через Request Problem Information = 0.
- **Topic Alias** позволяет скрыть реальное имя топика в логах — учитывать при аудите.
- **User Property** может содержать произвольные данные — не помещать туда секреты.
- **Server Reference** в DISCONNECT может уводить клиента на другой адрес — проверять доверие.

## 5.6. Практические рекомендации

**Для клиентов:**

- Всегда использовать TLS при работе через публичные сети.
- Проверять сертификат сервера.
- Не отключать проверку сертификата даже при отладке (использовать отдельный тестовый CA).
- Не передавать пароли в открытом виде.
- Хранить ключи и пароли в защищённых хранилищах.

**Для серверов (брокеров):**

- TLS обязателен для внешних подключений.
- Аутентификация — обязательна.
- Авторизация по топикам — обязательна в многопользовательских системах.
- Логировать подключения и отказы.
- Регулярно обновлять брокер и зависимости.
- Ограничивать максимальный размер пакетов и частоту подключений.
- Изолировать сессии при использовании общих Client Identifier.

**Для инфраструктуры:**

- Мониторинг брокера (метрики подключений, ошибок, нагрузки).
- Резервное копирование конфигураций и данных сессий.
- Плановая ротация сертификатов и ключей.
- Тестирование на проникновение в критичных развёртываниях.

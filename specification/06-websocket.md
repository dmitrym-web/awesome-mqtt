# 6. Использование WebSocket в качестве сетевого транспорта

## 6.1. Обзор

MQTT обычно работает поверх **TCP/IP**. Однако спецификация допускает использование и других транспортов, обеспечивающих:

- Упорядоченную доставку байт.
- Доставку без потерь.
- Двунаправленное соединение.
- Постоянное соединение (не запрос-ответ).

**WebSocket** (RFC 6455) — один из таких транспортов. Его основное преимущество — работа через стандартные HTTP/HTTPS-порты (**80** и **443**), что позволяет проходить через прокси, файрволы и корпоративные сети, где TCP-порт 1883 закрыт, а HTTP — нет.

Типичные сценарии:

- **Браузерные клиенты:** JavaScript не имеет доступа к сырым TCP-сокетам, но может использовать WebSocket API.
- **Корпоративные сети:** прокси пропускают только HTTP(S)-трафик.
- **Веб-приложения:** интеграция MQTT в SPA без дополнительных серверов-посредников.

## 6.2. Требования к WebSocket

Если MQTT работает поверх WebSocket, применяются следующие требования:

### 6.2.1. Обязательные условия

- WebSocket **ДОЛЖЕН** работать поверх **TCP**.
- **ДОЛЖНА** использоваться бинарная передача (`binary`).
- MQTT-пакеты **НЕ ДОЛЖНЫ** кодироваться как текстовые WebSocket-фреймы.
- Один WebSocket-фрейм **МОЖЕТ** содержать один или несколько MQTT-пакетов, или часть одного пакета — границы WebSocket и MQTT **НЕ** обязаны совпадать.

### 6.2.2. Согласование подпротокола

- WebSocket **ДОЛЖЕН** использовать подпротокол **`mqtt`**.
- Согласование происходит через HTTP-заголовок `Sec-WebSocket-Protocol`.
- Клиент отправляет: `Sec-WebSocket-Protocol: mqtt`.
- Сервер **ДОЛЖЕН** подтвердить этот подпротокол в ответе.
- Если сервер не поддерживает `mqtt` — соединение **ДОЛЖНО** быть закрыто.

Для MQTT 5.0 используется тот же идентификатор подпротокола — `mqtt`. Версия протокола определяется в самом CONNECT (Protocol Level = 5).

### 6.2.3. Маскирование

Правила WebSocket RFC 6455:

- Клиент **ДОЛЖЕН** маскировать все исходящие фреймы.
- Сервер **НЕ ДОЛЖЕН** маскировать исходящие фреймы.
- Сервер **ДОЛЖЕН** закрыть соединение, если получил немаскированный фрейм от клиента.

### 6.2.4. Ping/Pong WebSocket

WebSocket имеет собственный механизм Ping/Pong (контрольные фреймы). Он **НЕЗАВИСИМ** от MQTT PINGREQ/PINGRESP:

- WebSocket Ping/Pong работает на уровне транспорта и обрабатывается библиотекой WebSocket.
- MQTT PINGREQ/PINGRESP работает на уровне приложения.
- Оба механизма **МОГУТ** использоваться одновременно.
- WebSocket Ping/Pong **НЕ** должен использоваться вместо MQTT PINGREQ для проверки логики MQTT-сессии.

## 6.3. Формат пакетов

### 6.3.1. Инкапсуляция MQTT в WebSocket

MQTT-пакеты передаются внутри WebSocket-фреймов **как есть**, без изменений:

```
┌─────────────────────────────────────────┐
│         WebSocket Frame (binary)        │
├─────────────────────────────────────────┤
│  MQTT Control Packet (Fixed Header +    │
│  Variable Header + Payload)             │
└─────────────────────────────────────────┘
```

Правила:

- MQTT Fixed Header **НЕ** модифицируется.
- Remaining Length **НЕ** пересчитывается.
- Свойства, полезная нагрузка — без изменений.
- Границы WebSocket-фрейма и MQTT-пакета **НЕЗАВИСИМЫ**.

### 6.3.2. Объединение и разделение

Допустимы следующие варианты:

**Один фрейм — один пакет:**

```
Frame 1: [MQTT CONNECT]
Frame 2: [MQTT CONNACK]
Frame 3: [MQTT PUBLISH]
```

**Один фрейм — несколько пакетов:**

```
Frame 1: [MQTT CONNECT][MQTT SUBSCRIBE]
Frame 2: [MQTT PUBLISH][MQTT PUBLISH][MQTT PINGREQ]
```

**Несколько фреймов — один пакет:**

```
Frame 1: [первая часть PUBLISH]
Frame 2: [вторая часть PUBLISH]
```

Все три варианта корректны. Получатель **ДОЛЖЕН** собирать MQTT-поток байт из WebSocket-фреймов и разбирать его как обычный TCP-поток.

### 6.3.3. Порядок байт

- WebSocket сохраняет порядок байт.
- MQTT-поток байт **ДОЛЖЕН** интерпретироваться так же, как в TCP-соединении.
- Никаких дополнительных префиксов или суффиксов **НЕ** добавляется.

### 6.3.4. Закрытие соединения

- **MQTT-уровень:** клиент/сервер отправляет DISCONNECT. Затем WebSocket-соединение закрывается.
- **WebSocket-уровень:** одна из сторон отправляет Close frame.
- Порядок: **сначала** корректное завершение MQTT (DISCONNECT), **затем** WebSocket Close.
- Если WebSocket закрывается без MQTT DISCONNECT — считается аномальным отключением, Will-сообщение **ДОЛЖНО** быть опубликовано (с учётом Will Delay).

### 6.3.5. URI и порты

Обычные схемы URI:

- **`ws://`** — WebSocket без TLS (порт по умолчанию 80).
- **`wss://`** — WebSocket поверх TLS (порт по умолчанию 443).

Путь (path) задаётся брокером. Распространённые варианты:

```
ws://broker.example.com:80/mqtt
wss://broker.example.com:443/mqtt
wss://broker.example.com/mqtt
```

Конкретный путь — на усмотрение реализации брокера.

## 6.4. Практические замечания

### 6.4.1. Совместимость с TLS

`wss://` использует TLS на уровне WebSocket, что эквивалентно MQTT over TLS:

- Шифрование трафика.
- Проверка сертификата сервера.
- Возможность mTLS (взаимной аутентификации).

Все рекомендации раздела 5 (Безопасность) применимы.

### 6.4.2. Сравнение с TCP

| Критерий | MQTT over TCP | MQTT over WebSocket |
|----------|---------------|---------------------|
| Порт по умолчанию | 1883 / 8883 (TLS) | 80 / 443 (TLS) |
| Прохождение через прокси | Ограничено | Стандартно |
| Поддержка в браузерах | Нет | Есть |
| Накладные расходы | Минимальные | Чуть больше (заголовки WebSocket) |
| Задержка | Минимальная | Практически такая же |
| Поддержка на устройствах | Универсальная | Требует WebSocket-стека |

### 6.4.3. Производительность

- WebSocket добавляет 2–14 байт заголовка на фрейм.
- При больших пакетах накладные расходы незаметны.
- При частых коротких публикациях потери на заголовки могут быть значимы — иногда выгоднее объединять несколько MQTT-пакетов в один WebSocket-фрейм.

### 6.4.4. Ограничения

- **Нет доступа к сырому TCP:** некоторые оптимизации (например, TCP_NODELAY) недоступны.
- **Зависимость от библиотеки WebSocket:** клиент **ДОЛЖЕН** корректно обрабатывать фрагментацию фреймов и Close-фреймы.
- **Прокси-таймауты:** корпоративные прокси могут разрывать «простаивающие» соединения раньше, чем MQTT Keep Alive — иногда нужно уменьшить Keep Alive или отправлять PINGREQ чаще.

### 6.4.5. Пример клиента на JavaScript

Использование `mqtt.js` в браузере:

```javascript
import mqtt from 'mqtt';

// Через wss (TLS)
const client = mqtt.connect('wss://broker.example.com:443/mqtt');

client.on('connect', () => {
  client.subscribe('test/topic');
  client.publish('test/topic', 'Hello from browser');
});

client.on('message', (topic, payload) => {
  console.log(topic, payload.toString());
});
```

Внутри `mqtt.js` устанавливает WebSocket с подпротоколом `mqtt` и передаёт MQTT-пакеты в бинарном виде.

## 6.5. Соответствие

Клиент или сервер, поддерживающий MQTT over WebSocket, **ДОЛЖЕН**:

1. Использовать бинарные WebSocket-фреймы.
2. Согласовывать подпротокол `mqtt` через `Sec-WebSocket-Protocol`.
3. Корректно обрабатывать фрагментацию MQTT-пакетов между фреймами.
4. Корректно обрабатывать несколько MQTT-пакетов в одном фрейме.
5. Применять маскирование фреймов по правилам RFC 6455.
6. Использовать `ws://` или `wss://` (не голый TCP).
7. Завершать MQTT-сессию через DISCONNECT перед закрытием WebSocket.

Несоблюдение этих правил делает реализацию несовместимой с MQTT over WebSocket, даже если сам MQTT работает корректно.

# Приложение D. Рекомендации по реализации

Это приложение даёт рекомендации, которые **НЕ ЯВЛЯЮТСЯ** нормативными. Они помогают строить корректные и совместимые реализации, но отступление от них не делает реализацию несоответствующей — при условии соблюдения обязательных требований.

## D.1. Общие рекомендации

- **Проверяйте всё входящее.** Пакеты приходят из сети, им нельзя доверять. Любое нарушение формата — закрытие соединения.
- **Не полагайтесь на порядок.** Гарантия порядка действует только внутри одного соединения и одного топика с одинаковым QoS.
- **Не храните секреты в логах.** Пароли, токены, содержимое payload могут содержать чувствительные данные.
- **Обрабатывайте таймауты.** Все асинхронные операции (PUBACK, PUBREC, CONNACK) требуют таймаута.
- **Используйте разумные значения по умолчанию.** Например, Receive Maximum = 65535, Session Expiry = 0.

## D.2. Реализация клиента

### D.2.1. Подключение

- Всегда задавайте уникальный Client Identifier, если только не используете Clean Start = 1 с автоматической генерацией.
- Устанавливайте Keep Alive меньше, чем таймауты NAT/прокси в сети.
- Для публичных сетей — только TLS, только `wss://` или `mqtts://`.
- Реализуйте exponential backoff при переподключениях.

### D.2.2. Публикация

- Для QoS 1/2 храните исходящие сообщения до получения подтверждения.
- Используйте Message Expiry Interval для данных с ограниченным сроком актуальности.
- Для часто повторяющихся топиков используйте Topic Alias (если сервер поддерживает).
- Проверяйте Maximum QoS и Retain Available из CONNACK перед публикацией.

### D.2.3. Подписка

- Используйте Wildcards осторожно: `#` может привести к потоку данных больше ожидаемого.
- Для сценариев «ровно один получатель» применяйте Shared Subscriptions.
- Для отсечения собственных публикаций используйте NL = 1.
- Subscription Identifier полезен, когда один клиент подписан на несколько фильтров.

### D.2.4. Обработка ошибок

- Реагируйте на Reason Codes, не игнорируйте их.
- Логируйте Reason String для диагностики.
- При DISCONNECT с Server Reference — обновите адрес сервера.
- При ошибке аутентификации не зацикливайтесь на переподключениях — проверьте учётные данные.

### D.2.5. Управление сессией

- Для долгоживущих подписок — Session Expiry Interval > 0.
- Для коротких операций — Session Expiry = 0.
- Помните, что подписки и недоставленные сообщения сохраняются на сервере при persistent session.

## D.3. Реализация сервера (брокера)

### D.3.1. Приём подключений

- Ограничивайте частоту подключений с одного адреса (rate limiting).
- Проверяйте корректность CONNECT до создания сессии.
- Аутентификация — до CONNACK.
- Авторизация по топикам — при SUBSCRIBE и PUBLISH.

### D.3.2. Управление сессиями

- Отделяйте состояние соединения от состояния сессии.
- Ограничивайте общий объём хранимых сообщений на клиента.
- Используйте очередь с ограничением длины для ожидающих сообщений.
- Учитывайте Message Expiry при хранении.

### D.3.3. Доставка

- Не блокируйте общий поток на медленных клиентах — используйте очереди на клиента.
- При переполнении очереди применяйте политику (drop oldest / drop new / disconnect).
- Для retained — храните только последнее сообщение на топик.

### D.3.4. Обработка ошибок

- Разрывайте соединение при нарушении протокола.
- Возвращайте точные Reason Codes.
- Не раскрывайте внутренние детали через Reason String, если это не требуется.
- Логируйте аномалии (частые переподключения, ошибки авторизации).

### D.3.5. Масштабирование

- Кластеризация — на усмотрение реализации; спецификация не описывает.
- Синхронизация сессий между узлами — ответственность брокера.
- Retained и Will — общие для кластера или привязаны к узлу, в зависимости от архитектуры.

## D.4. Безопасность

- TLS — обязателен для внешних подключений.
- Пароли — только в виде хешей.
- Аутентификация — обязательна.
- Авторизация по топикам — обязательна в многопользовательских системах.
- Ограничивайте Maximum Packet Size для защиты от DoS.
- Ограничивайте Topic Alias Maximum.
- Не разрешайте неограниченные Subscription Identifier и Wildcards.

## D.5. Совместимость

- Поддерживайте MQTT 3.1.1 и 5.0 на одном порту (различие по Protocol Level в CONNECT).
- Не полагайтесь на MQTT 5.0-специфичные свойства при работе с 3.1.1-клиентами.
- Тестируйте с разными клиентскими библиотеками.
- Используйте официальные наборы тестов на соответствие.

## D.6. Отладка

- Ведите подробные логи на этапе разработки.
- Используйте Wireshark с диссектором MQTT для анализа трафика.
- Проверяйте поведение на граничных случаях: пустые payload, максимальные размеры, отсутствие подписчиков.
- Тестируйте разрывы соединений: kill -9, отключение сети, таймауты.

## D.7. Производительность

- Используйте TCP_NODELAY при малых сообщениях.
- Объединяйте мелкие MQTT-пакеты в один WebSocket-фрейм.
- Кэшируйте разобранные топики (для сопоставления с фильтрами).
- Избегайте блокирующих операций в обработчиках сетевых событий.
- Для высоких нагрузок — используйте пулы потоков и асинхронный I/O.

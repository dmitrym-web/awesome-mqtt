# 1. Введение

- **Глава 3 — Управляющие пакеты MQTT.** Описание каждого управляющего пакета.
- **Глава 4 — Операционное поведение.** Как взаимодействуют клиенты и серверы.
- **Глава 5 — Безопасность.**

В конце — приложения с нормативными утверждениями и сводкой изменений относительно предыдущих версий.

## 1.2. Терминология

- **Сетевое соединение (Network Connection)** — транспортное соединение поверх TCP/IP, по которому работает MQTT.
- **Сообщение приложения (Application Message)** — данные, передаваемые приложением через MQTT.
- **Клиент (Client)** — программа или устройство, использующее MQTT для подключения к серверу.
- **Сервер (Server)** — программа или устройство, принимающее подключения. Обычно называется **брокером (Broker)**.
- **Публикация (Publish)** — отправка сообщения клиентом на сервер.
- **Подписка (Subscribe)** — регистрация интереса клиента к топикам.
- **Топик (Topic)** — именованная метка, к которой публикуются сообщения. Иерархическая, разделяется `/`.
- **Фильтр топика (Topic Filter)** — выражение с подстановочными знаками `+` и `#`.
- **Тематический псевдоним (Topic Alias)** — целое число, заменяющее полное имя топика (новая функция MQTT 5.0).
- **Сессия (Session)** — состояние, хранимое сервером для клиента.
- **QoS** — уровень качества обслуживания (0, 1 или 2).
- **Will / Will Message** — «завещание»: сообщение, публикуемое сервером при аномальном отключении клиента.
- **MUST / MUST NOT / SHOULD / SHOULD NOT / MAY** — нормативные глаголы (см. RFC 2119, RFC 8174).

## 1.3. Нормативные ссылки

- **RFC 2119** — ключевые слова для указания уровней требований.
- **RFC 3629** — кодировка UTF-8.
- **RFC 6455** — протокол WebSocket.
- **RFC 8174** — уточнение к RFC 2119 о регистре ключевых слов.

## 1.4. Ненормативные ссылки

- MQTT Version 3.1.1 — предыдущая версия.
- MQTT-SN — версия для сенсорных сетей.
- Прочие статьи и реализации, перечисленные в конце спецификации.

## 1.5. Представление данных

### 1.5.1. Биты

Биты нумеруются от 0 (младший) до 7 (старший) в каждом байте. Поля описываются с указанием диапазона бит.

### 1.5.2. Двухбайтовые целочисленные значения

16-битные беззнаковые, big-endian (сначала старший байт). Диапазон 0–65535. Обозначение `uint16`.

### 1.5.3. Четырёхбайтовые целочисленные значения

32-битные беззнаковые, big-endian. Диапазон 0–4294967295. Обозначение `uint32`.

### 1.5.4. Строки в кодировке UTF-8

Кодированные в UTF-8 строки с предшествующим двухбайтовым полем длины (`uint16`). Завершающего нуля нет.

Пример: строка `hello` → `00 05 68 65 6C 6C 6F`.

Строки UTF-8 **не должны** содержать:
- U+0000 (нулевой символ);
- кодовые точки U+D800–U+DFFF (суррогаты);
- несимвольные управляющие коды.

При получении некорректной строки сервер **должен** разорвать соединение.

### 1.5.5. Двоичные данные

Передаются так же, как строки UTF-8, но содержимое может быть любым, включая нулевые байты.

### 1.5.6. Пары строк

Некоторые свойства (в MQTT 5.0) состоят из двух строк подряд: имя и значение. Каждая строка кодируется по правилам UTF-8.

## 1.6. Безопасность

Обзорная глава. Подробности — в [главе 5](05-security.md). Основные рекомендации: TLS, аутентификация клиентов, авторизация по топикам, осторожность с публичными брокерами.

## 1.7. Соглашения редактирования

- Все числовые поля — беззнаковые целые в big-endian, если не указано иное.
- Зарезервированные биты **должны** быть установлены в 0 и игнорироваться при приёме, если не указано иное.
- «Сервер» и «брокер» используются как синонимы.
- «Клиент» относится и к издателю, и к подписчику одновременно.
- Нормативные глаголы выделены заглавными буквами (MUST, SHOULD, MAY).
